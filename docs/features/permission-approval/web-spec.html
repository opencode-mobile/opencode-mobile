Permission approval for mobile

The web client already provides the interaction model: receive and queue blocking requests, explain the requested capability, respond once/always/reject, and recover from live events. Mobile has the response endpoint, but not the approval process.

Important: permission approval is an awareness and control mechanism, not a security sandbox. Displayed patterns are untrusted text and must never be transformed or executed.

Mobile v1 product behavior

Presentation

  • Persistent, non-dismissible Session Chat surface.
  • Permission category, explanation, and all patterns.
  • One request at a time with queue count.
  • Parent screen can surface child-session requests.

Submission

  • Allow once → once.
  • Deny → reject.
  • Disable both actions during submission.
  • Keep request visible until authoritative resolution.

Recovery

  • Never infer success after a disconnect.
  • Reconcile pending requests on reconnect.
  • Keep failures actionable with retry.
  • Use foreground in-app attention only.

What is missing today

  1. Correct wire values. Replace Android/iOS approve/deny serialization with once/reject.
  2. Pending request contract. Add typed request DTOs, list API, and ask/reply event payloads.
  3. Live store. Add idempotent reducers and reconnect reconciliation.
  4. Domain state. Add queue selection across parent and child sessions, response state, errors, and unseen attention.
  5. Reusable component. Build the state-aware design-system prompt before composing Session Chat.
  6. Native integration and tests. Match behavior, copy semantics, accessibility intent, and recovery on iOS and Android.

Acceptance gates

  • Live and recovered requests appear exactly once in the correct session tree.
  • Every pattern is visible without data loss.
  • Allow once sends exactly once; Deny sends exactly reject.
  • Repeated taps cannot duplicate a response; failure gives a retry path.
  • A reply removes only its matching request and advances the queue.
  • No mobile API or UI offers always, remember, auto-accept, or permission configuration.

Scope boundary

Excluded: persistent decisions, auto-accept, permission-rule editing, background SSE, push delivery, resolved history, and question-request UI.
