Attachments for mobile

Product term: Attachment (pending in composer, sent as domain FilePart). Upstream has no multipart upload API — bytes ride as data: URLs inside FilePartInput on prompt_async. Device photos/PDFs/text only; not project @ browsing.

Images · PDF · text/plain

End-to-end flow

1 · PickPhotos / Files (web: picker, paste, drop).
2 · AcceptMIME gate; reject other binaries.
3 · Encodedata:{mime};base64,…
4 · Sendprompt_async with text + file parts.
5 · ShowTimeline chips for data: URLs.
Scope split: In scope = device local upload as data URLs. Out of scope = project file:// / @ mentions (server reads disk).

Mobile v1 product behavior

Composer

  • Label: Attach / Add attachment.
  • Photos + Files pickers (no camera v1).
  • Removable pending chips; multi-attach.
  • Send allowed with attachments only.
  • Clear on HTTP 204; keep draft on non-2xx.

Domain

  • Attachment pending state.
  • FilePart on user messages.
  • Extend prompt send builders.
  • Post-204 errors via Session.Event.Error (no chip restore).

Excluded

  • Multipart / “upload” API.
  • Project file browser / @.
  • Drag-and-drop; camera; in-app PDF reader.
  • Hard client image resize.

Implementation slices

  1. Domain + DTO — file parts in/out, multi-part prompt_async.
  2. Design system — chip + file-part primitives before feature glue.
  3. Composer UX — pickers, chips, send gating.
  4. Timeline UX — image vs file attachment rendering.
  5. Validation — MIME, encode/send, history round-trip, both platforms.

Acceptance gates

  • Attach image, PDF, and text-like file; remove before send.
  • Unsupported type rejected without losing draft text.
  • prompt_async includes data-URL file parts; attachment-only send works.
  • Failed send keeps text + attachments; success clears pending chips.
  • History/SSE shows data-URL attachments on user messages.
  • iOS/Android behavior parity; intentional diffs in parity-gaps.md.
