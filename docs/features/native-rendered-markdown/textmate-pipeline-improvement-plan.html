TextMate Pipeline Implementation Plan

The six-phase execution plan for the selected TextMate pipeline architecture: one deep module with single ownership of mutable state, cooperative cancellation, incremental line reuse, explicit memory budgets, and release-grade performance gates.

ResponsivePlain content never waits for decoration; final work preempts history.
ReliableLatest-wins identity gates and owned native lifetime prevent stale or unsafe results.
ReusableOne request/result interface serves chat, history, gallery, tests, and future consumers.
FastPrepared line buffers, compiled programs, and incremental state remove repeated work.
MeasurableQueue, compile, tokenize, repair, cache, cancellation, and memory are separate signals.

Architect recommendation

Introduce one TextMateHighlightingEngine between Markdown fence discovery and semantic code decoration. Keep the outer DisplayMessagePipeline responsible for snapshot generation and publication; make the engine responsible for bounded highlighting and internal cache correctness.

Start with one active engine owner on each platform. Add a second isolated shard only if device measurements prove the single owner cannot meet throughput goals without harming foreground latency or memory.

Small external interface

interface TextMateHighlightingEngine {
  suspend fun highlight(
    request: HighlightRequest
  ): HighlightResult

  suspend fun trim(
    level: MemoryPressure
  )
}

Request contains

  • opaque fence key and monotonic revision token;
  • language, exact source, and policy epoch;
  • interactive-final, visible-history, or background-history intent.

Result contains

  • same identity plus canonical language;
  • ordered, non-overlapping semantic spans;
  • diagnostics and an all-or-nothing upgrade outcome.

Why this seam is deep

Hidden complexity

Grammar loading, rule compilation, regex objects, line state, native lifetime, cache policy, and repair versions stay internal.

Consumer leverage

Session Chat, viewport enrichment, Component Gallery, tests, and future code viewers share the same behavior without sharing internals.

Replaceable adapters

Joni and libonig remain internal platform adapters. Clock, metrics, and resource readers are test seams, not public API.

Cancellation and safety boundaries

Cooperative checkpoints

  • before every physical line;
  • every 64 regex searches;
  • before capture recursion and repair passes;
  • when a newer revision supersedes the block.

Initial work limits

  • 100,000 characters per highlighted block;
  • 20,000 characters per physical line;
  • intent-specific time and search budgets;
  • structured fallback rather than partial spans.

iOS ownership invariant

Every successful onig_new receives exactly one owner and eventually one onig_free.

  • decomposition probes are cached as owned candidates or freed immediately;
  • active searches hold leases so eviction cannot free in-use regexes;
  • allocation, free, live, peak-count, and estimated-byte metrics are required.

Scheduling and backpressure

Interactive final

Strict deadline priority. Latest revision wins. Queue cap: eight blocks.

Visible history

Viewport-relevant work ages so it cannot starve and remains cancellable.

Background history

Drops first under memory, thermal, low-power, or queue pressure. Queue cap: 24 blocks.

One active full TextMate job, at most 256,000 queued source characters, latest-wins coalescing, and 8:2:1 deficit service only when no interactive deadline is at risk. Plain publication never enters this queue.

Six-phase migration

1

Baseline and lifetime safety

Instrument stages, stress iOS first use/cancellation, fix decomposition leaks, count native allocation/free, and correct cache identity.

Status: closed on the named simulated correctness, lifetime, retained-state, fixture, and soak matrix.
2

Deep module and one owner

Introduce the engine behind existing preparation, serialize mutable state, and keep current fallback/final-upgrade behavior.

Status: closed. Injected lazy owner adapters, deterministic identity, exact-source checks, and pure attachment pass on both platforms.
3

Scheduling and backpressure

Add priority, coalescing, work limits, deadlines, trim handling, and queue/cancellation metrics.

Gate: plain budgets hold under a pathological highlighter.
4

Compiled programs and prepared lines

Use immutable rule programs, compact IDs, one UTF-8 map per line, weighted caches, and owned libonig leases.

Gate: exact oracles pass and reuse appears in metrics.
5

Incremental reuse

Add bounded prefix reuse, measure remaining repair cost, then add suffix convergence after multiline differential coverage.

Gate: incremental output equals full reparse.
6

Default enablement

Run device, pressure, thermal, cancellation, and soak matrices; promote only languages that meet correctness and latency gates.

Gate: all acceptance criteria pass on both platforms.

Phase 2 closure

  • The shared TextMateHighlightingEngine accepts one fence with an opaque key, monotonic revision, exact source, intent, and policy epoch.
  • Structural parsing produces a complete semantic-fallback document first; deterministic locators and pure attachment reject stale or mismatched results.
  • Android lazily creates one KMP/Joni runtime on its owner lane behind a mutex. iOS lazily creates one KMP/libonig runtime behind a Swift actor.
  • Joni and libonig regex caches are instance-owned, not process-global or thread-local production state.
  • Shared Android/JVM tests, the full iOS-simulator KMP suite, Android 24-way first-use stress, 17 focused iOS tests, and the simulator app build pass.

Reliability gates

Correctness and publication

  • complete source is always renderable;
  • only current generation, revision, and policy may publish;
  • incremental output equals full reparse;
  • final spans are ordered, bounded, non-overlapping, deterministic.

Operational safety

  • queue pressure changes decoration only;
  • eviction changes performance only;
  • leased regexes cannot be freed or orphaned;
  • both platforms share limits, outcomes, metrics, and interface tests.

Locked implementation decisions

1 · Engine seamDeep asynchronous post-parse fence-upgrade module.
2 · ConcurrencyOne active instance-owned serial KMP runtime initially.
3 · Memory24 MiB pooled eviction threshold; 32 MiB admission ceiling.
4 · LatencyOwned hypotheses become gates only after evidence-backed decisions.
5 · RolloutVersioned language allowlist beneath the global preference.

Phases 1–5 are closed. The shared asynchronous engine, deterministic fence identity, monotonic revision, exact-source validation, pure attachment, lazy single-owner Android/iOS adapters, and Phase 3 scheduling/backpressure policy are implemented. Physical release calibration remains mandatory in Phase 6. Phase 4 is next and owns compiled programs, prepared line buffers, and weighted caches.
