OPE-29

Rendered Markdown Highlighting Oracle Parity

Add trusted oracle fixtures around the markdown parser and syntax highlighter so large real-world responses, fenced code blocks, and fragile TextMate edge cases fail in tests before they regress visually in Session Chat.

Ticket Shape

SharedKMP markdown-core first
OracleShiki / vscode-textmate plus CommonMark
No UIQuality gate, not a renderer redesign
DocsMarkdown source plus this HTML view

What This Protects

High-risk markdown samples

Large assistant responses with multiple languages, nested fences, tables, lists, links, blockquotes, and raw HTML safety cases.

Syntax highlighting parity

Representative fenced code snippets compared against trusted Shiki or vscode-textmate token output.

Parser structure parity

Supported markdown constructs compared against a CommonMark-capable parser so handwritten parser drift is visible.

Platform bridges

Android/Joni and iOS/libonig paths stay covered where production highlighters should agree.

Implementation Flow

1. Inventory Collect existing regression samples: distributed scheduler, Python isolation, JS private fields, EventEmitter, HttpClient, and nested markdown fences.
2. Fixture Contract Define compact oracle JSON for parser blocks and highlighter tokens, separate from broad generated Shiki goldens.
3. Generators Extend Node tooling to emit trusted token fixtures and parser oracle snapshots deterministically.
4. Active Tests Add targeted KMP tests that compare shared parser and highlighter output to the oracle fixtures.
5. Decision Update docs with whether handwritten parser coverage is sufficient or migration to jetbrains.markdown should be planned.
