# ADR 0005: Single-Source App Launcher Icon

## Status

Accepted

## Context

The Android app ships an adaptive launcher icon (background color + foreground
vector + monochrome layer) and the iOS app needs a 1024×1024 app-icon set any
appearance plus a tinted silhouette for iOS 18. Before this decision the two
platforms maintained launcher art independently: Android had
`drawable/ic_launcher_foreground.xml` and `mipmap-*/*.webp`, while iOS had an
empty `AppIcon.appiconset` with slots but no images.

Hand-maintaining the icon per platform risks divergence (the glyph shape drifts
between platforms) and makes the iOS tinted silhouette easy to forget, since it
must track the foreground silhouette but is a separate rasterized PNG. The
project already has a precedent for generator-driven asset sync
(`scripts/sync-icons.mjs` for the Material Icons catalog), so a parallel
generator for the launcher icon fits the established pattern.

## Decision

Adopt a single canonical source SVG at `app-icon/source.svg` and a generator,
`scripts/sync-app-icon.mjs` (`npm run app-icon:sync`), that emits both platform
outputs from it.

The source SVG carries `<!-- @opencode/background -->` and
`<!-- @opencode/glyph -->` marker comments the generator parses. The generator
rasterizes flattened and silhouette 1024×1024 PNGs for iOS and rewrites the
Android adaptive-icon foreground vector, background color resource, and
adaptive-icon XML.

Rasterization uses `rsvg-convert` (librsvg), an external CLI dependency, rather
than a Node-native SVG renderer. This avoids adding a Node package dependency
and keeps the generator small; the trade-off is a system-level prerequisite
documented in `docs/design-system/app-icon.md`.

iOS `universal` and `dark` appearance slots share one flattened PNG (the
dark-background design reads in both luminosity modes). The `tinted` slot uses
a white-on-transparent silhouette derived from the same glyph paths so it stays
in sync automatically.

Android `mipmap-*/*.webp` raster fallbacks (for pre-API-26) are intentionally
not regenerated by the generator; modern Android uses the adaptive-icon XML
exclusively. Legacy fallback regeneration is a separate concern.

## Consequences

- Editing the launcher icon means editing one SVG and rerunning one script; iOS
  and Android stay consistent.
- The tinted iOS silhouette can never silently drift from the main glyph.
- `rsvg-convert` is a new system prerequisite for contributors running
  `app-icon:sync`; documented in the design-system doc.
- The stale `res/drawable/ic_launcher_background.xml` (green grid from the
  Android project template) is left unreferenced and unmaintained; it is not
  part of the adaptive icon and is not regenerated.
- Hand-edits to generated Android vector XML or iOS PNGs will be overwritten on
  the next sync; `app-icon/source.svg` is the only hand-edited **launcher**
  artifact.
- Store listing art is a separate source (`app-icon/interlock.svg` via
  `npm run app-icon:sync-store`) and must not replace the launcher pipeline.
  See `docs/design-system/app-icon.md`.
